Window-টা ১১৮০px-এ আঁকা (desktop app-এর মাপ); ছোট পর্দায় পাশে scroll করুন। সব নাম, সংখ্যা ও model উদাহরণ।

১Chat | Agent switch — composer-এ

কী: দুটো mode। Chat = আজকের আচরণ (এক প্রশ্ন, এক উত্তর)। Agent = কাজ শেষ না হওয়া পর্যন্ত AI নিজে পড়ে, লেখে, terminal command চালায়, ফল দেখে আবার চালায়।

কেন: CLI engine (claude/codex/gemini) হলে CLI-ই agent — আজ যেমন। API বা Ollama হলে daemon-এর নতুন SDC Agent loop চলে (ROADMAP §১, সিদ্ধান্ত ১–২)। ব্যবহারকারীর কাছে দুটোই এক switch — ভিতরের যন্ত্র কোনটা, সেটা জানার দরকার নেই। Mutation-এর আগে permission gate আর checkpoint দুই পথেই সমান।

২Model dropdown — শুধু connected, প্রতি family-র শেষ ২–৩ version

কী: তালিকায় সেই engine-ই ওঠে যেটা এখনই চলবে — CLI installed + signed-in, বা API key verified। প্রতিটা group-এর মাথায় connection badge (CLI · subscribed ✓ / API key ✓)। প্রতি family-র current ২–৩টা version; পুরনোগুলো "Older versions…"-এর ভিতরে। Disconnect থাকা provider তালিকায় নেই — footer-এ এক লাইনে গোনা, click করলে Provider Hub।

কেন: নীতি P4 — যে model বাছলে turn fail করবে তাকে দেখানোই মিথ্যা। তথ্যের তিনটা উৎস daemon-এ আগেই আছে (cli.recipes, keychain, provider.test) — নতুন method models.connected শুধু জড়ো করে।

৩Live thinking — অক্ষর-অক্ষর, শেষে এক লাইনে ভাঁজ

কী: Model ভাবতে শুরু করা মাত্র বেগুনি block-টা আঁকা শুরু হয় — dim italic, চলন্ত timer, লেখার শেষে cursor। ভাবনা শেষ হলে block নিজে ভাঁজ হয়ে এক লাইনের সারাংশ হয় ("Thinking · 6.2s"), click-এ আবার খোলে।

কেন: Claude Code-এর সমান অভিজ্ঞতা — আর ভিতটা (P3 structured stream, ThinkingBlock.tsx, live.ts) already আছে; এটা polish, নতুন নির্মাণ নয়।

৪Checkpoint timeline rail — Claude Code-এ যেটা নেই

কী: Stream-এর বাঁ কিনারায় একটা সরু রেখা; প্রতিটা mutation (Edit, Run, Save)-এর পাশে dot। সবুজ dot = checkpoint নেওয়া হয়েছে; hover = কী বদলেছিল; click = Time Machine ঠিক সেই মুহূর্তে।

কেন: এটাই "Claude Code-এর চেয়ে ভালো"-র উত্তর: শুধু কী ভাবছে নয়, প্রতিটা পদক্ষেপ থেকে ফেরার দরজাটাও দৃশ্যমান (P5)। Checkpoint গুলো daemon-এ প্রতিটা mutation-এ এমনিতেই তৈরি হয় — rail শুধু সেগুলোকে চোখের সামনে আনে।

৫Agent plan card — turn-এর মাথায়

কী: Agent mode-এ model প্রথমে ধাপগুলো ঘোষণা করে; card-টায় প্রতিটা ধাপ live tick হয় — শেষ (✓), চলছে (◉), বাকি (○)।

কেন: লম্বা agent run-এ সবচেয়ে বড় প্রশ্ন "এখন কী হচ্ছে, আর কতটা বাকি?" — plan card সেটার এক-নজরের উত্তর। Budget ছুঁলে বা ধাপ আটকালে ঠিক কোথায় থামল সেটাও এই card-ই বলে।

৬Verify chip — turn footer-এ, এক click-এ অন্য AI-র review

কী: প্রতিটা turn-এর নিচে Verify with… — engine বাছলে সেই turn-এর diff (checkpoint → এখন) reviewer engine পড়ে। ফলটা chip হয়ে turn-এই থেকে যায়: ✓ Verified · Gemini 3 Pro · 1 issue।

কেন: এক AI-র লেখা আরেক AI দিয়ে যাচাই — আপনার চাওয়া ৬। ভিন্ন model-এর ভুলের ধরন ভিন্ন, তাই cross-model review নিজের-review-র চেয়ে বেশি ধরে; আর diff-based বলে সস্তা (ROADMAP সিদ্ধান্ত ৩)।

৭Verify tab — দুই স্তর: যন্ত্রের check, তারপর AI-র চোখ

কী: উপরে আজকের চারটা row (typecheck / build / tests / lint) — এবার সত্যিই daemon চালায়, static নয়। নিচে AI reviewer-এর verdict: প্রতিটা issue-তে file:line (click = Preview সেই লাইনে) আর Fix with a prompt — এক click-এ fix-প্রস্তাবটা composer-এ।

কেন: যেটা যন্ত্রে ধরা যায় সেটায় token খরচ নয় — mechanical fail হলে AI ধাপ চলেই না। আর issue → file:line → fix prompt চেইনটা Error Translator-এর একই দর্শন: ভুলটা শুধু দেখানো নয়, ফেরার পথসহ দেখানো।

Approve করার আগে এই ৫টা দেখুন

  1. নম্বর ১–৭ প্রতিটা — রাখব, বদলাব, না বাদ দেব?
  2. Dropdown-এ "শেষ ২–৩ version + Older…" নিয়মটা ঠিক আছে, নাকি সংখ্যাটা অন্য হবে?
  3. Agent mode-এ permission-এর তিন স্তর (Simple = সব জিজ্ঞেস, Pro = লেখা auto/command জিজ্ঞেস, Auto = deny-list ছাড়া সব) — মানানসই?
  4. Checkpoint rail বাঁয়ে — নাকি dot গুলো card-এর ভিতরেই যথেষ্ট?
  5. রঙ/মাপ সব বিদ্যমান token থেকে — কোথাও চোখে লাগলে বলুন, token-এই ঠিক হবে।
